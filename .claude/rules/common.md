# 全プロジェクト共通ルール

> このファイルは `~/.claude/CLAUDE.md` から `~/.claude/scripts/sync-common-rules.ps1` で作ったコピーです。直接編集せず、元のファイルを直してからスクリプトを実行してください。
> クラウドセッションでは `~/.claude/` が読まれないため、リポジトリに置いています。PC では `claudeMdExcludes` で読み込みから外しています。

このファイルは、すべてのプロジェクトに共通する前提とルールです。
プロジェクト固有のルールは、各プロジェクトの CLAUDE.md に書きます。両方に書かれている場合は、プロジェクトの CLAUDE.md を優先します。

## 開発環境

### PC の場合
- PC にインストール済みのツールは `~/.claude/environment.md` に書いてある（クラウドセッションでは読めない）
- environment.md に書かれたツールはインストール済み。インストールの確認はせずに、そのまま使う
- PC 全体に新しいツールをインストールする場合は、理由を説明してユーザーに確認する。インストールしたら `~/.claude/environment.md` に追記する。アンインストールした場合は削除する

### クラウドセッションの場合
- OS は Ubuntu（Linux）、シェルは bash
- Flutter SDK はインストールされていない。必要な場合は、インストールを提案する
- Android エミュレータでの確認や、モックのスクリーンショットの撮影はできない。必要な場合は、その旨を報告して PC での作業に回す

### 共通
- バージョンが影響する場面（パッケージの追加・互換性の確認、ビルドエラーの調査など）でだけ、`flutter --version` などでバージョンを確認する
- コマンドが見つからないなどのエラーが出た場合は、原因を報告して指示を待つ
- プロジェクトの中だけで使うライブラリ（仮想環境に入れる Python のパッケージ、`pubspec.yaml` に書く Flutter のパッケージなど）は environment.md には書かず、プロジェクトの依存ファイル（と、あれば開発環境構築手順書）に書く

## コミュニケーション
- 回答・説明・コードコメントは日本語で書く（識別子・コミットのprefixは英語）
- 結論を先に、説明は簡潔に
- 要件が曖昧で、間違えると手戻りが大きい場合は実装前に質問する
- 要件に書かれていないことを決める必要がある場合は、勝手に決めずに質問する
- 推測で進めた部分は、最後にその旨を明記する

## 作業の進め方
- 1回の作業は1つのタスクに絞る。大きい場合は分割を提案する
- 実装前に、変更方針（触るファイル・やること）を短く示してから進める
- 変更は依頼された範囲に絞る。ついでのリファクタや無関係な整形はしない
- 既存のコード規約・命名・ディレクトリ構成に合わせる
- 新しい依存パッケージを追加するときは、理由を説明して確認を取る
- 実装後はビルド・テスト・Lintを実行して結果を報告する（コマンドはプロジェクトの CLAUDE.md を参照）

## 成果物（ドキュメント）

### 必須の成果物
次の6点を作ることを基本とする。

| ファイル | 役割 | テンプレート |
|---|---|---|
| `docs/要件定義.md` | 何を作るか。常に最新の仕様だけを書く | `.claude/templates/要件定義.md` |
| `docs/基本設計書.md` | どう作るか。機能・画面・メッセージ・モジュール構成・エラー処理など | `.claude/templates/基本設計書.md` |
| `docs/テスト仕様書.md` | 何をどうテストするか。テスト項目・手順・期待結果・結果 | `.claude/templates/テスト仕様書.md` |
| `docs/不具合一覧.md` | 見つかった不具合と、その対応 | `.claude/templates/不具合一覧.md` |
| `docs/品質報告書.md` | フェーズごとのテスト完了時の品質分析と完了判定 | `.claude/templates/品質報告書.md` |
| `docs/decisions/` | なぜそう決めたか。1件1ファイルの決定記録 | `.claude/templates/decisions/README.md` |

- 新規プロジェクトの開始時に、どの成果物を作るか、フェーズを分けるかをユーザーに確認する
- 成果物を省略する、フェーズを分けないなど、基本と違う判断をした場合は、その理由を決定記録に残す
- **ドキュメントを作るとき・書き足すときは、対応するテンプレートを読み、先頭の注記（`<!-- -->` の部分）に従う**。注記はプロジェクトのドキュメントにはコピーしない

### フェーズ分け
- MVP（フェーズ1）から始め、フェーズごとに要件を確定させてから設計・実装に入ることを基本とする
- 基本設計書・テスト仕様書は、要件が確定したフェーズの分だけ書き、フェーズが進むごとに追記する

### ID
- 要件は `REQ-001`、機能は `FN-001`、画面は `SCR-001`、メッセージは `MSG-001`、テスト項目は `TST-001`、不具合は `BUG-001` の形式で振る
- どのIDも振り直さず、別のものに使い回さない。削除しても欠番として残す
- 基本設計書・テスト仕様書・テストコードでは、対応する要件IDを必ず書く。テストコードにはテスト項目IDを書く

### 決定記録・未決事項
- 仕様や設計で何か決まったら、決定記録の追加と、要件定義（必要なら基本設計書・テスト仕様書）の更新をセットで行う
- 書いた決定記録は書き換えない。決定を変えるときは新しい記録を追加する
- 決定の経緯が必要なときだけ `docs/decisions/` を読む
- 要件に書かれていないため設計で仮に決めた箇所には【要確認】の印を付け、文書の付録「未決事項」にまとめる。未決事項は、ユーザーのレビューで確定させてから実装に入る

### 書き方
- ドキュメントは Markdown で書く。図は Mermaid で書く
- Mermaid の図の先頭には、矢印のラベルに左右の余白を付ける次の1行を入れる（図の種類ごとの書き方は基本設計書のテンプレートを参照）
  `%%{init: {'themeCSS': 'div.labelBkg { padding: 0 6px; background-color: rgb(232,232,232); } div.labelBkg span, div.labelBkg p { background-color: transparent; }'}}%%`
- `docs/` 配下のドキュメントのファイル名は日本語、フォルダ名・ソースコード・設定ファイルは英語。ファイル名にスペースは入れない（区切りはハイフン）
- 画面レイアウトは、動くモック（見た目だけで処理のない画面）のスクリーンショットで示す。モックの作り方はプロジェクトの CLAUDE.md に従う
- `docs/` 配下のドキュメント（決定記録を含む）には目次を付ける
  - 最初の `##` 見出しの前に `## 目次` を置き、`##` の見出しへの Markdown のリンクを箇条書きで並べる（`###` 以下は載せない）
  - Mermaid の図のリンクは目次に使わない（GitHub や VS Code のプレビューではクリックできない）
  - リンク先（アンカー）は VS Code のプレビュー・GitHub と同じ規則で書く：英字は小文字にし、記号（`.`・全角の括弧・コロン・中黒・`〜` など）は消し、空白は `-` にする。同じ見出しの2回目以降には `-1`・`-2` を付ける（例：`## 1. はじめに` → `#1-はじめに`）
  - 見出しを追加・変更・削除したら、同じ作業の中で Claude が目次も直す（VS Code の拡張機能には頼らない）
  - 目次の追加・更新は内容を変えないため、「書いた決定記録は書き換えない」の例外とする

## テスト
- 単体テスト・結合テストは自動テストを基本とする。実装後に Claude が実行し、結果を報告する。総合テストは手動で、ユーザーが実施する
- テストは `docs/テスト仕様書.md` の項目どおりに書く。実施したら、テスト仕様書の「結果・実施日」の列に記入する
- ロジック（UI に依存しないコード）を対象に、C0・C1 とも 100% を目指す。100% にできない箇所は、理由を説明してユーザーの承認を得る
- **テストが失敗したときに、期待値を変える・テストを消す・スキップするなどしてテストを通さない。テストを変える必要がある場合は、理由を説明してユーザーに確認する**
- コミット前に全テストを実行し、すべて通ることを確認する
- テストや通常利用で不具合が見つかったら、`docs/不具合一覧.md` に記録する。直したら、再発防止のテストを追加する
- フェーズごとのテスト（総合テストまで）が終わったら、`docs/品質報告書.md` に品質分析を書き、次のフェーズに進んでよいかの判定をユーザーに確認する

## コード品質
- 読みやすさを優先し、関数は小さく保つ
- 画面（UI）とロジックを分離し、ロジックは UI に依存しない形で書いてテストする
- マジックナンバーは定数化する
- エラーは握りつぶさず、適切に処理またはログ出力する
- 「なぜそうしたか」が自明でない箇所にだけコメントを書く

## 安全
- APIキー・パスワード・トークンをコードやコミットに含めない（.env等を使い、.gitignoreを確認する）
- ファイル削除、git push、force系操作、DBの破壊的操作は実行前に必ず確認する
- 秘密情報を含むファイル（.env など）の内容を出力しない

## Git
- コミットメッセージは Conventional Commits 形式（feat: / fix: / docs: / refactor: / test: / chore:）。不具合の修正では、メッセージに不具合ID（BUG-）を書く
- 1タスク＝1コミット
- コミットは、ユーザーがレビューして承認してから行う

## 環境
- PC：OS は Windows。シェルコマンドは PowerShell で動く書き方を優先する
- クラウドセッション：OS は Ubuntu（Linux）。シェルコマンドは bash で書く
- パス区切りやファイルの改行コードの違いに注意する

## モデルの使い分け

使用量の上限があるため、モデルは opusplan（Plan Mode 中は Opus、それ以外は Sonnet）を基本とし、判断の重い作業だけ Plan Mode で行う。

### 作業ごとの目安
| 作業 | 進め方 |
|---|---|
| 要件定義・基本設計の方針決め、決定記録 | Plan Mode（Opus） |
| 原因がわからない不具合、設計変更を伴う修正 | 原因調査と修正方針までを Plan Mode（Opus）、承認後の修正は通常モード（Sonnet） |
| 設計書の清書・体裁調整、実装・テストコード作成、通常の不具合修正 | 通常モード（Sonnet） |
| 品質報告書の分析・振り返り | 通常モード（Sonnet）。考察が詰まったら Plan Mode |
| ファイル検索・一覧作成など定型作業（サブエージェント） | Haiku を指定する |

### ルール
- 作業の開始時に、目安と現在のモードが合わなければ、Plan Mode への切り替えを一言提案する。切り替えるかはユーザーが判断する
- 同じ不具合の修正に2回失敗したら、Plan Mode で原因を調べ直すことを提案する
- クラウドセッションでは opusplan を使えないため、判断の重い作業は Opus、それ以外は Sonnet を目安にし、合っていなければ /model での切り替えを提案する
