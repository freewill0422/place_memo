テンプレートの注記（プロジェクトのドキュメントにはコピーしない）

全体
- テストで見つかった不具合も、通常利用で見つかった不具合も記録する
- 不具合が1件もない場合も、このファイルを作る。その場合は「一覧」の表がヘッダ行だけになり、「詳細」の節は見出しだけになる
- 「一覧」の表と、1件ごとの「詳細」の2段で書く
- 軽微な不具合（表記ゆれ・誤字程度）は一覧の1行だけでよく、詳細は書かない

ID
- 不具合ごとに BUG-001 形式のIDを振る。振り直さず、削除しない

一覧の列
- ID／概要（1行で何が起きるか）／重要度／状態／発見日／発見工程／原因の分類／テスト項目ID／要件ID／機能ID／修正日
- 該当しない列は「—」とする（通常利用で見つけた場合のテスト項目ID、原因がまだ分からないときの原因の分類など）

重要度
- 高：アプリが落ちる、データが壊れる・消える
- 中：機能が仕様どおりに動かない
- 低：見た目・表記の誤り

発見工程
- 単体テスト／結合テスト／総合テスト／通常利用 のいずれか

原因の分類（原因が分かった時点で記入する）
- 要件の漏れ：要件定義に書かれていなかった、または曖昧だった
- 設計の誤り：要件は正しいが、基本設計書の内容が誤っていた
- 実装の誤り：設計は正しいが、コードが誤っていた
- テストの漏れ：テスト項目やテストコードが不足・誤っていて、見つけるべき工程で見つけられなかった

状態（作業に合わせて更新する）
- 未対応：記録しただけで、まだ手を付けていない
- 対応中：修正している
- 修正済み（未コミット）：修正とテストが終わり、ユーザーのレビュー待ち
- 完了（コミット済み）：ユーザーが承認し、コミットした
- 対応しない（→ 決定記録の番号）：直さないと判断した。理由は決定記録に書く

修正とコミット
- 不具合を直したら、同じ現象を確かめる再発防止のテストを追加し、テスト仕様書に項目を追記する（「対応」の列に BUG- のIDを書く）。そのテスト項目IDを詳細の「再発防止テスト」に書く
- ユーザーが承認したら、状態を「完了（コミット済み）」にし、修正日を記入してから、修正と同じコミットに含める
- コミットメッセージには不具合IDを書く（例：fix: 最後の画像で→キーを押すと落ちる問題を修正 (BUG-001)）。どのコミットで直したかは git log --grep=BUG-001 で探す

詳細の書き方（例）
### BUG-001 最後の画像で→キーを押すと落ちる
- 現象：フォルダ内の最後の画像を表示中に→キーを押すと、アプリが終了する
- 再現手順：
  1. 画像が3枚あるフォルダの3枚目を開く
  2. →キーを押す
- 期待結果：何もしない（REQ-024）
- 原因：一覧の範囲外を参照していた（image_list.py）
- 対応内容：末尾で次へ進まないよう修正した
- 再発防止テスト：TST-112
